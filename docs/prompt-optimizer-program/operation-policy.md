# Prompt Optimizer operation policy

Status: binding for this program. Amend within authorized scope only through a decision recorded in `ledger.md`; material scope, permission, data-transmission, cost, or external-action changes require explicit user authorization that the ledger merely records.

## Product invariants

- Project initialization, bounded inspection, review, and consent precede Prompt Optimizer use.
- DWI remains standalone; future external systems enter only through evidence-backed adapters.
- Local navigation does not call a provider. Provider transmission requires an explicit disclosed action.
- The deterministic candidate remains measurable and recoverable through baseline promotion.
- Semantic output is accepted only as a valid, current, bounded V2 patch.
- One shared question policy permits at most three material questions and prefers zero.
- One structural call budget permits at most three calls; a third call requires evidence and a named trigger.
- Assessment has no arbitrary tools, shell, workspace writes, or task execution.
- Prompt and project content do not enter reusable logs, identifiers, or metrics.
- A simulator proves only the contract and failure behavior it actually exercises.
- Deterministic source attention, context allocation, authority ordering, and safety gates remain authoritative through the standalone baseline. Learned or self-training components are deferred to separately authorized, preregistered post-baseline experiments and may later advise only within deterministic validation; they cannot own consent, approvals, spending, safety decisions, or phase gates.

## Delivery invariants

- The repository and observed behavior outrank planning assumptions.
- Each phase has one owner, a frozen `expected.md`, explicit non-goals, evidence, and rollback.
- A phase closes only with no unwaived acceptance item and verification on the exact review SHA.
- Experiments do not become product behavior without predeclared held-out evidence.
